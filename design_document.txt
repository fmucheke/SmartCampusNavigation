# DESIGN DOCUMENT – Smart Campus Navigation (Final Submission)

Team: Urisha Shrestha, Franklin Mucheke, Samriddi Upreti

## 1. PROGRAM OVERVIEW

Our program helps users find campus facilities, navigate between buildings and explore the university's department structure.

We used three main data structures: a custom hash table, a graph and a general tree.

The program loads buildings.txt, connections.txt, facilities.txt and departments.txt in that order. Incorrect records are rejected with warnings, while valid records continue to load.

The Final version contains 18 menu options.

## 2. HASH TABLE AND FACILITY MANAGEMENT

We created a custom hash table to make facility ID searches faster.

The hash function is:

    h = 0
    For each character c in the facility ID:
        h = (h * 31 + c) % capacity

The default capacity is 101 buckets and does not resize.

We used separate chaining, where each bucket contains a vector of facilities. If two IDs go into the same bucket, both can still be stored. For example, F001 and F039 both go into bucket 16.

A collision is counted when a new facility is successfully inserted into an occupied bucket. Duplicate IDs are rejected.

Facility IDs are standardized before hashing. Name and category searches use linear search and ignore capitalization.

The category report groups facilities by category and calculates their counts and percentages.

## 3. CAMPUS GRAPH

We used an undirected graph to represent buildings and their connections. Each building has a list of neighboring buildings, called an adjacency list.

We chose an adjacency list because not every building is connected to every other building. It allows us to store only the connections that exist.

Breadth-First Search (BFS) uses a queue to visit nearby buildings before moving farther away.

The shortest path function also uses BFS. It remembers the previous building at each step and reconstructs the path once the destination is reached. The shortest path is based on the fewest connections.

The connectivity report displays building and connection counts, highest-degree buildings, isolated buildings and connected components.

## 4. DEPARTMENT TREE

We used a general tree because a department can have multiple departments under it.

Each node stores its department name, a parent pointer and a vector of children. The first accepted department becomes the root. Duplicate names and unknown parents are rejected.

The program supports adding departments, searching by name and displaying the hierarchy.

We implemented three traversals:

- Preorder: Visits the parent before its children.
- Postorder: Visits the children before their parent.
- Level-order: Visits departments one level at a time.

Preorder and postorder use recursion, while level-order uses a queue.

The department statistics show total departments, leaf departments, tree height and maximum number of direct children. Height is measured in edges and displays N/A for an empty tree.

The destructor deletes child nodes before their parents to release allocated memory.

## 5. PROGRAM ORGANIZATION

We separated the program into different classes so each team member could work on their assigned module.

- Facility, FacilityManager and HashTable manage facility records.
- CampusGraph and GraphLoader manage buildings and connections.
- DepartmentNode and DepartmentTree manage the department hierarchy.
- FileUtils provides shared name-standardization functions.
- main.cpp connects all modules and displays the menu.

## 6. TIME COMPLEXITY

F = Number of facilities

V = Number of buildings

E = Number of connections

D = Number of departments

C = Number of facility categories

| Operation | Time Complexity |
|---|---|
| Facility ID search | O(1) average with short chains, O(F) worst case |
| Facility name/category search | O(F) |
| Facility category report | O(F × C) |
| BFS reachability | O(V + E) |
| Shortest path | O(V + E) |
| Graph connectivity report | O(V + E) |
| Department addition and search | O(D) |
| Department traversals | O(D) |
| Department statistics | O(D) |
| Department tree deletion | O(D) |

The category report can take O(F²) time in the worst case. Hash table searches may become slower as the chains grow because the capacity is fixed.

These calculations assume constant-time name comparisons.
